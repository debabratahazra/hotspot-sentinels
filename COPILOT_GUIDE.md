# HotSpot Sentinels — Copilot Project Blueprint & Implementation Rules

## 1. System Mission
HotSpot Sentinels is an AI-driven urban climate resilience system built for the Google Cloud AI Builder Cup under the "Sustainability and Social Impact" theme. It ingests urban aerial/satellite imagery and local telemetry, uses Gemini 2.5 Flash on Vertex AI for multimodal analysis, identifies urban heat island (UHI) hotspots, calculates a Heat Vulnerability Index (HVI), recommends passive cooling designs (cross-ventilation and cool-roof retrofits), and publishes automated alerts to Pub/Sub when critical thresholds are exceeded.

## 2. Hard Technical Constraints
- Model & SDK: Exclusively use the modern `google.genai` SDK (`from google import genai`) with `gemini-2.5-flash`. Do not use the legacy `vertexai.generative_models` namespace.
- Region: Default to `asia-southeast1` (Singapore) across all services. **One narrow exception:** a BigQuery job must run in the location of the data it reads, and `bigquery-public-data.noaa_gsod` is US multi-region. `climate_service.py` therefore uses `BIGQUERY_LOCATION`, default `US`. Pinning `asia-southeast1` there makes every telemetry lookup fail into the fallback. This exception applies to that public-dataset read only; every resource this project owns stays in `asia-southeast1`.
- Backend Framework: FastAPI (Python 3.10+) with async route definitions.
- Runtime Target: Google Cloud Run containerized via multi-stage Docker.
- Data Persistence: Google Cloud Firestore for scan results and action plans.
- Object Storage: Google Cloud Storage for satellite crops and heatmaps.
- Event Broker: Google Cloud Pub/Sub for alerts.
- Metric Units: Always use standard metric units (Celsius °C, metres m, square kilometres km²).

## 3. Data Schemas

### Heat Analysis Result Schema (JSON)
```json
{
  "zone_id": "string",
  "zone_name": "string",
  "coordinates": {"lat": 1.3521, "lng": 103.8198},
  "ambient_temp_c": 36.5,
  "hvi_score": 8.4,
  "risk_level": "CRITICAL",
  "surface_breakdown": {
    "asphalt_pct": 55,
    "dark_roof_pct": 30,
    "concrete_pct": 10,
    "green_canopy_pct": 5
  },
  "passive_cooling_plan": {
    "corridor_orientation": "NE-SW (aligned with prevailing monsoon winds)",
    "retroreflective_coating_sqm": 4200,
    "micro_canopy_interventions": ["Plant shade corridors along West-facing asphalt", "Install shade sail pergolas"],
    "projected_surface_temp_drop_c": 6.8
  },
  "alert_dispatched": true,
  "timestamp": "ISO-8601 UTC"
}
```

### HVI Risk Bands

`risk_level` is derived from `hvi_score`, never chosen independently:

| HVI score | risk_level | Behaviour                                             |
| --------- | ---------- | ----------------------------------------------------- |
| < 4.0     | `LOW`      | —                                                     |
| 4.0–5.9   | `MODERATE` | —                                                     |
| 6.0–7.9   | `HIGH`     | —                                                     |
| >= 8.0    | `CRITICAL` | Publishes a Pub/Sub alert; `alert_dispatched` is true |

`surface_breakdown` percentages are integers that sum to 100. All temperatures are °C and all areas are m².

### Application envelope fields

`main.py` adds these to the API response and the persisted scan. They are owned by the application, never generated by Gemini, and are additive to the schema above:

| Field            | Values                               | Meaning                                                                                                               |
| ---------------- | ------------------------------------ | --------------------------------------------------------------------------------------------------------------------- |
| `climate_source` | `bigquery` \| `fallback` \| `caller` | Where `ambient_temp_c` came from: live NOAA GSOD, the 38.5 °C offline fallback, or a caller-supplied what-if override |

`POST /api/analyze` accepts an optional `ambient_temp_c` multipart form field. When supplied it must be finite and inside the ratified −50 °C to 60 °C range, it replaces the telemetry lookup entirely so no BigQuery query is issued, and `climate_source` becomes `caller` — an auditor must never mistake a what-if number for measured telemetry. An out-of-range or non-numeric value is rejected with the standard `{code, message}` envelope before any cloud call.

`alert_dispatched` is set by `main.py` from the Pub/Sub publish result — it means *an alert was successfully published*, not *the score was high enough*. `vision_analyzer` always emits `false`.

`identity_source` is owned by `vision_analyzer` and records, per field, whether the zone identity was supplied by the caller or inferred by the model. Coordinate components are tracked independently:

```json
{"zone_id": "supplied", "zone_name": "inferred",
 "coordinates": {"lat": "supplied", "lng": "inferred"}}
```

An inferred identity is a vision-model guess with no ground truth, so a consumer must never present it as authoritative. The field is absent on records written before it existed; absence implies neither origin.

`image_source` records where the analysed image came from — `caller` for an upload, `google_maps` for imagery fetched from the Maps Static API for a coordinate. `attribution_required` is `true` for Maps imagery, which Google's terms require be displayed with its attribution watermark intact and never cropped.

`POST /api/analyze` accepts **either** a `file` upload **or** an `imagery_lat`/`imagery_lng` pair, never both and never neither — either mistake is a 422. Those imagery fields are distinct from the optional `lat`/`lng` identity fields, which describe an uploaded image rather than requesting one. A coordinate used to fetch imagery is always `supplied` in `identity_source`. A Maps failure is a 502; an invalid coordinate is a 422.

### Additive-field checklist

When adding or changing a report-envelope field, update and verify every layer in the same change:

- Canonical report schema: `.github/skills/heat-report-validation/assets/heat_analysis_result.schema.json` (base report properties and compatibility rules).
- `backend/main.py`: `AnalysisResponse` and the serialized HTTP response.
- `backend/services/database.py`: persisted Firestore record; envelope fields must survive save/read unchanged.
- This guide: application-envelope definition and provenance semantics.
- `.github/skills/heat-report-validation/scripts/validate_report.py`: allowed envelope field set and validation rules.
- `tests/test_contract.py` and `tests/test_cross_layer_contract.py`: positive/negative schema cases and the application-to-validator field-set regression guard.

`AnalysisResponse` is the application source of truth for additive fields. A field added there is not complete until the validator and both contract-test layers recognize it; the cross-layer guard intentionally fails on that drift.

### Ratified limits

| Limit                         | Value                      |
| ----------------------------- | -------------------------- |
| Max upload                    | 10,000,000 bytes (decimal) |
| Accepted upload types         | `image/jpeg`, `image/png`  |
| Plausible ambient temperature | −50 °C to 60 °C            |
| Dashboard HTTP timeout        | 5 s connect, 60 s read     |
| Readiness-check timeout       | 5 s                        |
